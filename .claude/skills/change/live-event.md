# A live event

Events tell a client that something changed so it can refetch. An event is not the data and never carries a secret or customer data. The stream is built (`antilog-server/src/api/live.rs`, `antilog_types::LiveEvent`, `GET /events/stream`); the web app (`web/src/api/live.ts`) listens, and falls back to its 4-second poll when the stream fails. What is not built is the events table with its own types: the stream announces rows that already exist, see below.

## How events work

- One stream from the server (`antilog-server`), server-sent events, `GET /events/stream`, scoped to the signed-in member's organization. A client only receives events for what that member may read: every read goes through the organization's row-level security and the same check as the REST route for it (`floor::experiment`). It is authenticated when it opens, checks the credential and the membership again every 30 seconds (`Options::recheck`) and ends when either no longer holds, so a revoked token or a removed member is cut off within that interval; it also ends after 4 minutes and the browser reconnects.
- Each event has a kebab-case type (the SSE `event:`), the JSON of the whole event (`LiveEvent`, in the OpenAPI document), and an `id:` where it matters. The events: `hello`, `resync`, `message` (a conversation item was added to a session), `session` (its status changed) and `cards` (the number of cards waiting for this member changed). They carry ids, a status and a count, never words, a card's text or a secret.
- The first message on a connection is `hello`, and a client refetches what it shows. The `id:` of `hello`, `resync` and `message` is a `session_events.seq`. A client that reconnects sends `Last-Event-ID` and receives the `message` events after it. If it is more than 2,000 items behind, or ahead of the ledger, the first message is `resync` and the client refetches what it shows. `session` and `cards` have no id: they describe state, and the `hello` after a reconnect makes the client refetch it.
- The action layer publishes the event after the write commits (see [write-action.md](write-action.md)). Reports of session state, messages and spend, and a measurement arriving for a `measure` ticket, come in as writes, so they publish events the same way.
- Events are rows, built so far for the conversation: the stream replays `session_events` (append-only, written in the same transaction as the change) by `Last-Event-ID`. Session status and cards are read from their own tables (`sessions.updated_at`, the pending cards) and announced when they change. No Redis. (target: a general events table written by the action layer, and pruning past a replay window; the conversation table is never pruned today.)
- An open stream polls Postgres from the server: new conversation items every second, sessions and cards every second poll. Polling keeps the server free of `LISTEN/NOTIFY` connections. The stream ends after 4 minutes (a comment line every 10 seconds keeps proxies from closing it early), and the browser reconnects with `Last-Event-ID`.
- **The client.** `web/src/api/live.ts` opens one `EventSource` in the signed-in shell, refetches the queries an event makes stale (`staleBy`), closes the stream in a hidden tab and opens it again when the tab shows, and tells the queries (`liveStatus.ts`) to stop polling while it delivers. If the stream is refused or closed for good it tries again after 30 seconds and the pages poll every 4 seconds meanwhile. A session that is Done or Failed stops its own transcript refetch. The `history` tool call is never refetched by an event: a tool call made without a session opens one, and a session is an event.

## Adding an event

1. Add a variant to `LiveEvent` in `crates/antilog-types/src/live.rs` (give a variant with fields `#[serde(rename_all = "camelCase")]`, which utoipa needs) and make `crates/antilog-server/src/api/live.rs` produce it, scoped like the others. (target: publish it from the action layer, never from a handler.)
2. Regenerate the document and the TypeScript client by [api-endpoint.md](api-endpoint.md). The event union is part of the document and is snapshotted.
3. Tell the web app and the Mac app which screens refetch on it; the boards say which state changes (see [screen.md](screen.md)).
4. Tests, in `antilog-server/tests/api.rs` (`mod live`) and `web/e2e/live.spec.ts`: the stream replays after a gap, sends `resync` when it cannot, ends at its age limit, and another organization's events never arrive. (target: after a stream ends at the cap on Lambda, and publishing after commit only.)

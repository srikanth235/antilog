# Behaviour

How a screen behaves. Every client shares behaviour and words, not pixels. The mockup of the web client is `design/web/` (a clickable prototype, see [`design/web/README.md`](../../../design/web/README.md)).

- **Mockups first.** Every visual or UX change starts in `design/`: edit the parts in `design/web/src/` and run `bash design/web/src/assemble.sh`. See [`design/README.md`](../../../design/README.md).
- **The web app is organised around experiments as sessions (target).** Mockup: `design/web/`. The three basics still own everything underneath; the screen is not split by them.
  - **Frame.** A fixed 256px sidebar and a main area. Sidebar top: Search, Projects, Dashboard, Customize, More (Run history, Settings). A primary "New experiment" button. Then Pinned, then experiments grouped under collapsible project headings: one line each, a run count and one status icon. The six statuses (Running, Draft, Win, Merged, No win, Stopped) each have their own icon shape, never colour alone. The user menu at the bottom has Settings, a quick light and dark switch, host name and Sign out.
  - **An experiment is one thread.** A header (title, status, primary metric baseline to best so far, run, trials, spend of budget, elapsed, Stop run with an inline confirm, Pin, menu), a chart of the primary metric per trial with baseline and noise band, then a conversation: the request, Ratchet in short sentences, the draft card (expanded until approved, then one summary line), an eight-step stepper coloured by owning area, expandable trial cards (agent, change, files, measured value against baseline, delta, one outcome tag, diff, guardrail metrics, holdout), notes from people, and the result card with lineage in three columns (Experiment, Data, Compute), Open pull request and Run again. A composer is docked at the bottom and follows the state: change the draft, steer the next trial, or start another run with a note.
  - **New experiment** asks one question, "What do you want to improve?", with a text box and pills that open popovers: Project, Evaluation, Skills, Data, Environment, Agents, Budget, Guardrails and paths. "Draft experiment" creates the session at once as a Draft. Nothing is created in the customer's cloud until Approve.
  - **Projects** is a page of project cards. A card opens a project page with a summary and a table of its experiments.
  - **Customize** is one page with five tabs: Evaluations, Skills, Connectors, Agents, Plugins. A Yours / Discover toggle, search, filter and sort, and an Add menu per kind. Discover shows a featured banner (a carousel for connectors), a "For you" grid whose "+" becomes a check, and a "New" section with Show all. Configure opens the same detail-page layout for every kind.
  - **Global search** is a centred palette opened from the sidebar, the top bar, Cmd/Ctrl+K or "/". Scopes: All, Experiments, Projects, Datasets, Customize, Runs, People. With no query it shows Needs attention, Recents and Actions. Results are grouped by kind with the match highlighted, and each opens the exact place: a trial opens its thread with that trial expanded. The footer shows only keys that work.
  - **Other pages.** Dashboard (value per year, spend, Return, win rate, accepted wins), Run history (Trials and Instances tabs).
  - **Settings is a dialog, not a page.** It opens over the app from the user menu, More, or a Settings result or action in search, so you keep your place. It is a large centred dialog with a dimmed backdrop, a title bar with a close button, and a left rail with a search field. Focus moves into the dialog and Tab stays inside it. Esc (the first Esc clears the rail search), the close button or a click on the backdrop close it and return focus to what opened it. The rail is grouped by whose setting it is, with a hairline between groups: **You** (Profile, Appearance, Notifications, Access tokens) and **Organization** (General, Users and groups, Single sign-on, Budgets, Notes, Audit logs). It reopens on the section you used last. The rail search filters sections and rows by title, description and keywords, and opens the first section that matches.
  - **A setting is a row.** The title (Item weight) with a one-line muted description under it on the left, the control on the right (switch, select, segmented control, field, button), and a hairline between rows. A sub-setting is indented under its parent and is disabled while the parent is off. A section can have several headed groups. A list inside Settings (users, groups, access tokens, per-experiment budgets, audit logs) is a quiet table: column headers, an icon or avatar and name with a muted second line, a tag for a kind, an icon and word for a status. No cards inside cards.
  - **Organization settings are read-only for non-owners, not hidden.** Owners change them. Editors and viewers see the same section with its controls disabled, a one-line explanation ("Only owners can change roles. You can read them.") and a lock beside the section in the rail. Notes can be added by editors and owners. An organization always keeps at least one owner. The theme is one setting with two places to change it: Appearance, and the quick switch in the user menu.
  - **Narrow screens.** Below 720px the dialog is full-screen and the rail becomes a search field with a select of sections.
  - **Reuse the patterns.** One detail-page layout, one popover, one palette and one dialog. A new kind of thing under Customize uses them; it does not get its own page style. Menus and popovers close on an outside click. Every menu item is a `.mi`, every select uses the `.selw` wrapper, and every control has a disabled style.
- **One set of page states.** Every page uses the same six: loading, empty, failed, refused, partial, not checked. Each says what happened and what to do, in a sentence. Failure is never drawn as empty or zero, and something not checked is never drawn as healthy.
- **The holdout is marked.** A holdout dataset always shows as "Restricted to evaluator" and cannot be granted to agents. The grant control is absent for it, not disabled. A skill, a plugin or a connector never changes that. (target: datasets and grants are not built yet.)
- **A new optimization is a short declaration.** The user states the goal and limits, then picks context and infrastructure that already exist. Setting those up happens elsewhere, once, under Customize. (target. Today New optimization is a wizard over repository, benchmark template, agents and AWS.)
- **A command that spends or changes things shows what it would do first.** Confirm after the preview, never before. In the web app that is Draft, then Approve: the draft shows what would run and what it may cost, and nothing is created until Approve. A destructive step such as Stop run confirms inline.
- **A control says exactly what it does.** A control that does nothing is deleted. A footer or menu lists only keys and actions that work.
- **Same in every client.** If the web app, the CLI and MCP disagree about state or words, one is wrong.
- **Status is never colour alone.** Every status and outcome has a word, and a status has its own icon shape.
- **Accessibility.** Targets, labels and focus are checked in the web prototype.

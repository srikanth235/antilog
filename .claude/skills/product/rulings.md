# Rulings

Everything here is target; nothing is built on this branch. Each section is dated and says who directed it.

## The design: a chat and a judge (target)

Directed by the owner, 16 Nov 2026. It replaces the earlier design (see "What this replaces").

- **Ratchet is a chat and a judge.** The chat works like Claude Code on the web: a person talks to a coding agent in a sandbox with repos attached. The judge is a set of tools every session gets. Only the judge's numbers count, and only a measured win becomes a pull request. There are no modes, no plan step and no orchestration loop on the server, and nothing sits between a session and its experiment (see "What this replaces").
- **Three objects.** An **experiment** (the sealed goal and everything measured against it: a definition of better (metric and direction, the evaluation (a command and its protected files), guardrails, the data (evaluation data and a holdout), repeats and the acceptance criteria), then its trials, scoreboard, wins, receipts, watch and budget; the definition is immutable once sealed, a change makes a new version of the same experiment, numbers never carry across versions; state Not sealed, Sealed, Watching or Regressed; activity from its sessions). A **session** (one agent's work inside an experiment: a chat with one agent in one sandbox on one agent platform, with any number of repos; it always belongs to an experiment and is not a top-level noun in the app; status Working, Waiting for you, Done or Failed; a session a person stops is Done, "Stopped by NAME"; on screen it is named by its agent, "Claude Code session"). A **measurement** (the judge's signed result for one trial). A **trial** is one `measure` call: a set of commits (one per repo changed), the trial it started from and a one-line hypothesis. Every experiment belongs to a **project**, a group for one area of the code (see "Projects and Customize come back"). Everything else (scoreboard, wins, receipts, value, Return) is a view over measurements.
- **The tools.** Every session gets the Ratchet tools, and `ratchet mcp` (target) serves the same tools to an agent a person already uses on their own machine, so a change can be proposed anywhere and is measured only by the judge. Work tools: `seal`, `measure` (asynchronous: a ticket now, the measurement later as an event), `history`, `spawn`, `deliver`, `watch`. Setup tools, each shown as a card: `attach_repo`, `request_credential`, `set_environment`, `request_budget`. The pages are [session tools](../session/tools.md) and [judge tools](../judge/tools.md).
- **Settings are tools.** A person approves the tool calls that matter, and settings pages list what was approved. Setup happens in the chat, at the moment it is needed, as a card. Policy (Settings, Approvals) can pre-approve a card kind: Always ask, Allow up to a limit, or Allow. Add credential always asks and can never be pre-approved, because a person types the value into a secure form that goes straight to the platform's credential store. Roles decide who may approve which card; a viewer approves nothing. The audit log lists tool calls that changed something and approvals. Settings pages read and revoke; they are not where setup begins. Two things are still set up in Settings: agent platform accounts (self-hosted) and members and sign-in. Connectors and agents are registered once in Customize, but a chat can ask for the same thing with an Add credential card, so nothing waits on it. See [organization approvals](../organization/approvals.md).
- **Approval cards.** Seal experiment, Raise budget, Add credential, Attach repo, Change environment, Open pull request. Defaults: Seal experiment asks; Raise budget asks above the limit set in Settings, Approvals; Attach repo asks; Change environment asks; Open pull request asks.
- **The judge.** A separate trait from the agent platform trait: run this command at these commits with these secrets and return these numbers. The trust rules never bend: only the judge's numbers count; an agent never holds the holdout credential; a sealed experiment never changes; a person or an agent can never mark a win, only the acceptance criteria can, as one pure function in code; chat can change what an agent tries and never what counts. See [judge rules](../judge/rules.md).
- **The anti-cheat is built into the judge.** A sealed experiment (a hash over the definition and its protected files at pinned commits; a trial that changes a protected path is Rejected). A separate judge sandbox for every measurement (fresh, no agent in it, the only place with the holdout credential, a network route only to the experiment's data, removed afterwards). Seal checks before an experiment can be sealed (the baseline, the noise check, the cheat checks). Confirm before Kept (measured again in a fresh judge sandbox and checked on the holdout, with a bar that rises with the number of trials tried). A second opinion from an agent of a different model provider than the proposer, which flags and never decides. A signed receipt. See [judge anti-cheat](../judge/anti-cheat.md).
- **Acceptance.** A trial is Kept when it beats the trial it started from (the baseline or a Kept trial) by more than the bar, every guardrail holds, and it is confirmed in a fresh judge sandbox and on the holdout. An experiment's best is its best Kept trial. Outcomes: Measuring, Kept, Within noise, Worse, Guardrail failed, Failed holdout, Rejected, Failed.
- **What an agent sees.** The measured value and guardrail values on the evaluation data, and the outcome. It may read the evaluation's code, since that lives in a repo, and may never change it. It never reads the holdout or learns a holdout value. This replaces the earlier rule that an agent never reads the evaluation's code.
- **Delivery and watch.** `deliver` opens one pull request per repo changed, linked to each other, each carrying the receipt, and refuses any trial that is not Kept. The session stays attached: review comments and CI failures arrive in the chat, and a rebase is measured again before the receipt is updated. After delivery the experiment can be watched; a regression (worse than the delivered value by more than the noise) wakes a session or starts a new one in the experiment, and notifies.
- **Memory is `history`.** Each trial carries its hypothesis, so a later session reads what was tried and what failed, failures included. There is no notes feature. Skill packs (see "Projects and Customize come back") are written know-how a person adds, not a record of what was tried: `history` stays the memory of trials.
- **Starting.** The Home composer ("What do you want to improve?", chips Project, Repos, Agent, Environment, Budget) starts a new experiment in a project, with its lead session. Until a person seals it from the Seal experiment card the experiment is Not sealed: the agent explores, measures the baseline and proposes a definition with `seal`. An experiment may stay Not sealed and end there.
- **Sessions.** One agent per session. A session attaches any number of repos, and protected paths in an experiment name their repo. Git is the hand-off: each session gets a short-lived git token per repo that pushes only to that session's own branch, and Ratchet stores commit ids, never diffs. A session may spawn others in the same experiment, on the same budget, on any agent and platform; a spawned session cannot spawn; spawned sessions appear as cards and a person can open any of them, as its own chat inside the experiment, and talk to it. No agent's vendor is privileged, because only the judge decides. The agent drives: the only server-side state machines are the judge's queue and the budget meter. See [session rules](../session/rules.md).
- **Budget.** One per experiment, covering all its sessions and their judge time. Spend is model tokens, sandbox time and judge time. It is set when starting, from a Budget chip on the composer that defaults to the organization's default from Settings, Budgets. An editor or owner can change it at any time: from the scoreboard strip ("Change budget"), the experiment detail page or a row on the Seal experiment card; lowering it below what is spent stops new measurements. The agent can still ask with `request_budget`, which shows a Raise budget card. When it is spent the judge refuses `measure` and the experiment is Waiting for you with a Raise budget card. An experiment's budget sits inside its project's optional monthly cap, which sits inside the organization's monthly cap, and no budget can pass either.
- **The sandbox is temporary, the conversation is not.** A sandbox ends when the session is idle or stopped, and resuming starts a new sandbox from the session's branches.
- **What the server stores.** The conversation (what people and agents said), tool call names and card states, commit ids, measurements, spend and audit rows. Never tool output, file contents, diffs or data. Tool output and raw logs stay on the platform, are fetched when someone opens them, and may expire; the session says so.
- **What agents are told is part of the product.** The session brief, the tool descriptions, how history is shown and when to stop live in one place, are versioned and are tested against a set of repos with known wins. See [session prompts](../session/prompts.md).
- **The organization floor.** Members and roles (owner, editor, viewer; the organization role is the default in every project, and a project can set a member's role for itself), projects, sign-in, access tokens and service accounts, approvals and policy, budgets, the audit log and notifications (a win, Waiting for you, a regression, a budget spent).
- **The screen.** A fixed 256px sidebar (brand, New experiment, Search; the rows Projects and Customize; Pinned; then experiments grouped under collapsible project headings, one line each with an activity icon, and under an experiment that is open or pinned its sessions nested one level deeper; user menu) and a main area. New experiment is a composer ("What do you want to improve?") with five chips (Project, Repos, Agent, Environment, Budget), not a dialog or a form. An experiment page is the chat of its lead session with the scoreboard strip under a header that links to Details; spawned sessions appear as cards and open as their own chat inside the experiment (breadcrumb "Project / Experiment title / Codex session"). A composer lets a person talk at any time, including to interrupt. A card is the only place structured output appears. Projects is a list page and each project a detail page. Customize is one page with tabs Evaluations, Skills, Connectors, Agents and Plugins, each with a Yours and Discover toggle, and every item opens the one DetailPage layout. An experiment has a detail page (the definition, seal checks, scoreboard, history of trials across sessions, wins, watch and versions); a win has a receipt page. Settings is a dialog with a rail. Page types: Session (the experiment page and its session chats), ListPage, DetailPage, Dialog, SettingsSection, SignIn. See [design behaviour](../design/behaviour.md).
- **The chat's voice is Ratchet.** An agent's message shows the Ratchet mark and the name "Ratchet", with the agent that did the work as a quiet second label ("Ratchet · Claude Code", "Ratchet · Codex" in a spawned session). Agent logos stay where an agent is the subject: spawned session cards, the Agent chip, settings rows, receipts and lineage. Directed by the owner, 16 Nov 2026.
- **Clients.** The web app; the installed web app on Windows and Linux; the `ratchet` CLI, where `ratchet "cut checkout p95"` opens the same session in the terminal (target); `ratchet mcp`. The native macOS app stays ruled in; its boards are removed until the web direction is approved.
- **Principles.** The ten governing principles are in [SKILL.md](SKILL.md).

## What this replaces

Directed by the owner, 16 Nov 2026. These were the earlier target design. They are removed, not renamed, except where a row says otherwise.

| --- | --- |

| The stepper and its side wizard | Cards in the conversation. |
| Customize, Evaluations, Skills, Plugins, Connectors and Agents pages | Cut on 16 Nov 2026, then brought back the same day as one Customize page (see "Projects and Customize come back"). Setup in the chat as a card still works, and what a card adds appears in Customize. |

| Skill packs | Cut, then back as versioned written know-how the judge never reads (see "Projects and Customize come back"). `history` stays the memory of trials. |
| Notes, and Pause agent | Cut. A person talks to the agent. |
| Projects | Cut, then back with roles per project (see "Projects and Customize come back"). |
| The dashboard page | Cut. The Projects page holds Delivered, Pending and Return. |
| The three basics: optimization, context, infrastructure | Experiment, session, judge and organization floor. |
| The evaluator, the evaluator sandbox, the measuring platform | The judge, the judge sandbox, the judge platform. |
| Benchmark and evaluation template | The experiment's evaluation, inside a sealed experiment. A reusable evaluation template is back under Customize, Evaluations, and a sealed experiment starts from one. |

The agent loop's ideas survive in the judge: trials, Kept, confirmation on the holdout and agents that build on each other's best.

## Brought back from v1, 16 Nov 2026, at the owner's request

Directed by the owner, 16 Nov 2026. The good parts of the first design (commit 0ca52bf) return in forms that fit a chat and a judge. Everything here is target.

- **Connectors.** Connectors first returned under Settings and moved to Customize the same day (see "Projects and Customize come back"). They have: a list (logo, name and target, status Connected, Reconnect or Not checked, last checked, used by N experiments), a catalogue picker, a detail page with "How access is scoped" and a Datasets table, an Add connector page per system (an MCP server has its own), and an error page that shows datasets as Not checked, never empty. Connectors are Snowflake, Databricks, BigQuery, Postgres, DynamoDB, Amazon S3 and an MCP server. The code host is not a connector; repos stay under Settings, Connections.
- **Two credentials per connector.** Each is registered once, with a recipe, and kept in the platform's credential store. Ratchet keeps neither. The agent credential is read-only on the views listed and leaves out the holdout. The judge credential is separate and also covers the holdout. Both are short-lived and minted per session. The Add credential card is connector-aware and offers "Browse connectors".
- **Datasets and the holdout.** Datasets live under a connector. A dataset version never changes. A holdout is a marking on a dataset, enforced by the credentials; the grant control is absent, not disabled, and the row reads "Restricted to the judge". A holdout value never appears in history, a message or a receipt shown to an agent.
- **Receipt lineage.** The receipt gains Data (dataset versions, commits, credential scopes used) and Compute (judge platform and environment, judge image and digest, agents and sessions). "Signed by the judge" keeps Verify again and its checks. The Open pull request card previews the repo, branch, title and files changed, "Worth $X a year. Stays Pending while open." and "Nothing merges until a person merges it."
- **Value.** A win counts as Delivered once its pull request is merged. Pending is not in Return. The Projects page keeps the Delivered, Pending and Return strip, and there is no experiments list page.
- **Agents.** An Agents table (agent, platform, model, parallel limit, used in N experiments, last used) and an agent page with "What the agent holds". It first sat in Settings, Agent platforms and moved to Customize the same day. Settings, Agent platforms keeps platform accounts only.
- **Sessions and clean-up.** The experiment detail page lists its sessions with spend, state and clean-up (Removed, Not removed), with a banner when one is not removed. Settings, Budgets shows spend by experiment and by session. A spawned session card shows its spend of the budget.
- **Evaluation kinds as templates.** Speed, Quality, Size and Cost, with templates (Load test, Query latency, Test suite duration, Bundle size, Forecast error, Your own). The Seal experiment card shows the kind and its planted cheats. The templates are listed under Customize, Evaluations (see "Projects and Customize come back").
- **Small things.** @-mention of a session in the composer, and a one-time prompt after the first measurement, "Notify me when this experiment needs me".
- **Rules restored.** One translator per outside system; Ratchet never reshapes or pipes data; a session contacts only the endpoints its experiment and environment allow; each agent its own session and branch; a stopped session is ended and deleted at once; choosing agents is not part of what better means.
- **Still out.** Notes, the dashboard page, agent order, Pause agent and per-agent budget shares. Featured and For you marketing in the catalogue, and the stepper, stay out too. (Customize, projects, skill packs and plugins were out here and came back; see below.)

## Projects and Customize come back, 16 Nov 2026, decided by the owner

Directed by the owner, 16 Nov 2026, after the first rework. It reverses the cut of projects, Customize, skill packs and plugins, and it amends the "What this replaces" table and the decided call 4 below. Everything here is target.

- **Projects.** A project groups the experiments for one area of the code. Every experiment belongs to exactly one project. A session still belongs to an experiment, so the chain is project, experiment, session.
- **Roles per project.** A project has members as owner, editor or viewer. A person's organization role is their default in every project, and a project can set someone's role for that project. Organization owners manage organization settings. Project owners manage the project's members and budget. Permission checks run at project scope, and approving a card needs the right role in the project the experiment is in. See [organization model](../organization/model.md).
- **The Projects page and the Project page.** Projects is a list page: each project with the person's role, experiments, wins and spend this month, and New project. Delivered, Pending and Return across experiments sit at the top of it. A project page is a DetailPage: the title, the person's role, counts, a description, New experiment, an Experiments table (experiment, baseline to best, state, activity, budget and spend), Connectors used, Budget and Members. A project with no experiment has its own empty page.
- **Budget.** An experiment's budget, which a person can still change, sits inside its project's optional monthly cap, which sits inside the organization's monthly cap. The default budget per experiment can be set per project and falls back to the organization default.
- **New experiment asks for the project.** The composer gains a Project chip (Project, Repos, Agent, Environment, Budget), defaulting to the project the person is in.
- **The sidebar.** From the top: brand, New experiment, Search, the rows Projects and Customize, then Pinned, then experiments grouped under collapsible project headings, one line each with an activity icon. Under an experiment that is open or pinned its sessions are nested one level deeper, each named by its agent with its status icon. The user menu stays at the foot.
- **Customize.** One sidebar page with tabs Evaluations, Skills, Connectors, Agents and Plugins, each with a Yours and Discover toggle. It is a library of reusable things. Setting them up in the chat with a card still works, and what a card adds appears here. Every item opens the one shared DetailPage layout, and a new kind of item gets no page style of its own.
  - **Evaluations** are reusable evaluation templates (kind Speed, Quality, Size or Cost; command; direction; guardrails; the standard planted cheats; environment). A sealed experiment starts from one, and the agent drafts a seal from a template. The seal checks (baseline, noise, cheats) stay the judge's.
  - **Skills** are versioned skill packs: written know-how that agents read. The judge never reads a skill pack, a pack never holds holdout data, and an experiment records the versions read (the receipt's Data column). In docs it is a "skill pack", so it is not confused with this repo's `.claude/skills/`. See [session add-skill-pack](../session/add-skill-pack.md).
  - **Connectors** and their datasets and holdout moved here from Settings. Settings, Connections keeps only the repos, credential references and environments approved in chats, and links to Customize, Connectors.
  - **Agents** and the agent page moved here from Settings. Settings, Agent platforms keeps platform accounts only, and links to Customize, Agents.
  - **Plugins** are bundles that add evaluations, skill packs, suggested connectors and recommended agents under their own kinds. A plugin has no powers of its own: it can never mark, unmark or grant access to a dataset. Removing a plugin asks whether to keep its items, and an item in use by an experiment is never removed.
- **Words.** "Project", "Customize", "Skill" (on screen; "skill pack" in docs), "Plugin" and "Evaluation" (a reusable template, and the command inside a sealed experiment) are no longer retired. Still retired: contract, run (as a noun), draft, thread, evaluator, measuring platform, notes as a feature, the dashboard page, Pause agent, agent order and the stepper.

## Offerings, platforms and vendor facts (target)

Decided by the owner, 16 Nov 2026, unchanged by the redesign.

- **Two offerings.** Self-hosted: the Ratchet server is a Docker Compose service (server and Postgres) in the customer's infrastructure, using the agent platform accounts the customer already has, at least one. Ratchet cloud: we host the server and run every session on Ratchet's platform accounts, billed to the customer at cost through the budget. Both ship from day 0, and one core serves both.
- **Ratchet runs no sandboxes for agents. Agent platforms do.** An agent platform is a managed service that runs an agent and its sandbox as one durable session: Claude Managed Agents, AWS AgentCore, the OpenAI Agents API, Microsoft Foundry Agent Service and Google Agent Runtime. Every platform sits behind one agent trait with one adapter each: start a session with repos, an agent, an environment, credentials and tools; send input; read its events; stop it and delete it. Platform words stay inside each adapter. Foundry Agent Service and Google Agent Runtime run a container image Ratchet supplies, so on these two Ratchet supplies one agent image per agent, with the agent's own harness inside it.
- **An agent is a model on a platform.** For example Claude on Claude Managed Agents, Codex on the OpenAI Agents API, Gemini or Grok on AgentCore, which runs one harness over many model providers, GitHub Copilot (Copilot SDK) on Microsoft Foundry Agent Service, and Gemini (ADK) on Google Agent Runtime.
- **Build order.** The traits are designed against all five platforms from the start. Adapters ship in this order: Claude Managed Agents, AWS AgentCore (which brings Gemini and Grok), the OpenAI Agents API, Microsoft Foundry Agent Service, Google Agent Runtime.
- **Where the judge sandbox runs.** On a platform that can run a command in a sandbox with no agent. AWS AgentCore can. Google Agent Runtime sandboxes run without an agent; whether one can hold a credential the agent never sees is checked in the spike. Claude Managed Agents, the OpenAI Agents API and Microsoft Foundry Agent Service cannot. Foundry has no sandbox that runs a command with no agent, and its Code Interpreter is a tool the agent calls, so the likely path there is a judge image deployed as a hosted agent that runs only our measuring code and no model.
- **`measure` is asynchronous so no platform limit applies.** On Foundry, a client tool is answered by returning a `function_call_output` with the call id, and a documented 10-minute expiry for tool outputs may apply. On Google Agent Runtime serving tools over the event stream is not documented, and bidirectional streaming is in preview with a 10-minute limit per query. Returning a ticket at once and delivering the measurement later as an event sidesteps both. The spike checks it.
- **Credentials reach a session only through the platform's credential store** (the Claude Managed Agents vault; AgentCore Identity; the agent's Microsoft Entra agent identity on Foundry Agent Service, with secrets reached through a Foundry connection to Azure Key Vault; the agent's Agent Identity or service account on Google Agent Runtime, with secrets read from Secret Manager; or the platform's equivalent). The exact stores on the last two are confirmed in the spike, as Agent Identity is partly in preview. Never a prompt, a file in the repo or Ratchet's database. Model access belongs to the platform account, so no model key enters a sandbox.
- **Connectors** an agent's code may read: Snowflake, Databricks, DynamoDB, BigQuery, Postgres, Amazon S3 and any MCP server. The code host (GitHub, GitLab) is how repos attach and pull requests open. Each connector says how to make a read-only, holdout-excluding credential for its system. The customer registers it once, and it lives in the platform's credential store, never in Ratchet. Credentials minted per session may come later, connector by connector, and need a new ruling.
- **Ratchet cloud uses only Ratchet's platform accounts at launch.** An enterprise cannot bring its own platform accounts to Ratchet cloud yet, though the adapters support customer accounts because self-hosted needs them. An enterprise that needs data read in its own network self-hosts, for example with AgentCore in its own AWS account.
- **Timing is noisier on shared sandboxes.** Platform sandboxes run on shared hardware, so a timing experiment's noise band is wider and fewer trials are Kept. The noise check and the bar handle it, and the experiment detail page says so in one line.
- **No Helm chart and no OpenTofu at launch.** The self-hosted server ships as Docker Compose only. Ratchet cloud ships with the Cloudflare config and `cf`. Ratchet's own platform accounts are set up by hand, written down and owned by the owner. Either tool comes back only with a new ruling.
- **"This machine" is deferred.** Agents never run on a Mac until a later ruling, after the first platform ships. Measuring never runs on a laptop either way.

## Ratchet cloud (target)

Decided by the owner, 15 and 16 Nov 2026, unchanged by the redesign.

- **Storage.** Self-hosted uses Postgres 18. Ratchet cloud uses one SQLite database per organization, inside one Cloudflare Durable Object per organization, pinnable to the EU, the US or FedRAMP. Both ship from day 0. Moving between them is an export and import of one neutral file format, not a database copy.
- **One core, two shells.** `ratchet-core` holds all logic and the API routes and compiles natively and to WebAssembly. Storage sits behind one trait with two implementations. `ratchet-server` is the self-hosted shell; `ratchet-cloud` is the Cloudflare shell. A small shared directory holds sign-in routing and billing, never tenant data. See [stack](../stack/SKILL.md).
- **We manage everything.** Ratchet cloud runs the server on Cloudflare and every session on Ratchet's platform accounts. An organization signs in, attaches repos and starts; it runs no infrastructure of its own.
- **Ratchet's platform credentials** sit in Cloudflare's Secrets Store, bound to the Worker, never in an organization's database, a response or a log.
- **We are a data processor** for every Ratchet cloud organization: a data processing agreement, listed subprocessors (Cloudflare and the agent platforms in use: Anthropic, OpenAI, AWS, Microsoft, Google) and a stated retention rule. Ratchet keeps no tool output, file contents or diffs; each platform's own retention is stated beside it. The vendors promise only where data is stored at rest. Foundry Agent Service keeps data at rest in the geography of the chosen Azure resource; where the model processes it depends on the model deployment type (Standard and Regional stay in the geography, Data Zone stays in the US or EU zone, Global can be anywhere). Google Agent Runtime keeps data at rest in the location chosen (the US or EU multi-region, or a supported country); where it is processed is checked in the spike. Today the OpenAI Agents API offers data residency in the United States only and no zero data retention.

## Sign-in (target)

- **Sign-in is OpenID Connect, plus GitHub's OAuth.** Ratchet cloud offers GitHub (OAuth with its user API, since GitHub does not offer OpenID Connect for app sign-in), Google (OpenID Connect), and an organization's own OpenID Connect provider (single sign-on), which only an owner sets up. A self-hosted server uses the administrator's OpenID Connect provider. No passwords.

## Desktop clients (target)

Decided by the owner, 14 and 15 Nov 2026, unchanged by the redesign.

- **A native macOS app, SwiftUI, macOS only at launch.** It is a client of the server's API. It stays ruled in; its boards are removed until the web direction is approved.
- **On Windows and Linux the desktop app is the web app, installed as a progressive web app.** The same web client, installable from Chrome or Edge: its own window and taskbar icon, a badge for what needs attention, push notifications and an offline screen. On macOS the web app does not offer to install; it points to the Mac app.
- **Notifications are in the product:** a win, Waiting for you, a regression, a budget spent. Native on the Mac, web push elsewhere, ids only. See [organization notifications](../organization/notifications.md).
- **The device stores no data either.** The service worker caches the app's own files only, never API responses, diffs or logs. A push message carries ids only; the app fetches the rest when opened. A self-hosted server that cannot reach the browsers' push services sends no push, and everything else works.
- **Clients share behaviour, words and element ids, never pixels.** See [design behaviour](../design/behaviour.md).
- **The Mac app is a direct download, updated with Sparkle.** It is signed with a Developer ID and notarized, not on the Mac App Store. It checks one signed update feed, ours, daily by default; a person can turn checks off, and a company can turn them off for its Macs and deploy releases itself through device management, which is also how air-gapped installs update. See [stack/swift/ratchet.md](../stack/swift/ratchet.md).

## Still unproven: the spike

The spike comes before any product code. One tiny experiment is measured end to end on all five platforms. It proves the agent trait, the Ratchet tools served to a session over its event stream (undocumented on Google, a 10-minute expiry on Foundry; asynchronous `measure` is designed to sidestep both) and a judge sandbox that holds a credential no agent sees.

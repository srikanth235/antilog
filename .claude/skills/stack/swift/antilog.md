# Swift and SwiftUI in Antilog (target)

Nothing of this exists yet. Its boards are owed once the web direction is approved. The macOS app is SwiftUI and macOS only. Windows and Linux use the web app ([../typescript/antilog.md](../typescript/antilog.md)). Versions are in [libraries.md](../libraries.md), including Sparkle, which updates the app outside the Mac App Store. This page says how the app is written and checked when code lands.

## Toolchain (a proposal until the owner confirms)

- Swift 6 language mode with complete concurrency checking, SwiftUI, built with Xcode 27 against the macOS 27 SDK. The deployment target is macOS 26, a proposal: check API availability before using anything newer, and do not raise the target for one API call.
- Do not weaken the language mode, turn off strict concurrency, or suppress a diagnostic to get a build.

## Workflow and done criteria

Build and test from the command line, with the project's own settings (the exact project, scheme and destination are written here with the first code):

```bash
xcodebuild -project Antilog.xcodeproj -scheme Antilog -destination 'platform=macOS' test    # (target)
```

**Done** when the build and tests pass on macOS 26 or later, your change adds no warnings and no force unwraps or `try!` in app code, and user-triggered failures reach the user. If the toolchain is unavailable (this repository's agent sessions often run on Linux), say the Apple build and tests were **not run**; do not call the change done on a reading of the code ([land/report.md](../../land/report.md)). Generated files (colours, words, the API client) are regenerated by their generators, never edited.

## The app (target)

- **An API client only.** The app talks to the server through the same API as the web app, from types generated from the OpenAPI document. It runs no agent and no sandbox. **The judge never runs on the Mac**: the app never holds the holdout credential or produces a number that counts.
- **Shell only.** The server owns product rules, screens' content and user-facing words. The Swift shell renders state and performs requested platform effects. **Do not invent product rules or user-facing strings in the shell.** A literal string, colour or rule in a view is a finding.
- **Share behaviour, words and element ids with the web app, never pixels.** Use the system's chrome: window, toolbar, sidebar, Settings window, menu bar, notifications. Each view sets the same accessibility identifiers as the web element ids ([design behaviour](../../design/behaviour.md)).
- **Generated, not hand-written (target).** Colours come from `design/tokens.toml` and words from the one words catalogue, written as Swift by the generator, light and dark. Use semantic colours (`Color.antilogCanvas`-style names the generator emits) and the system's dynamic type; no hex in a view.
- **Sign-in is OpenID Connect in the browser.** Use `ASWebAuthenticationSession` (needs a presentation context anchor: the key window), with PKCE. The app never shows a password field and holds no long-lived cloud or holdout credential. Tokens live in the Keychain (`SecItem`), never in `UserDefaults` or a file. Sign-out clears them.
- **The menu bar item.** A `MenuBarExtra` is an entry point showing the running state (sessions that are Working or Waiting for you, spend against the budget) with a few actions; everything it shows is also reachable from the main window. Its icon is a template image. Details: [general/macos.md](general/macos.md).
- **The Settings scene.** A `Settings` scene holds preferences of this Mac only: the server address, launch at login, notifications. Organisation data and roles are the server's and appear in the web app and the main window, not here.
- **No helper process.** The app bundles nothing that runs agents or sandboxes. Agents run as sessions on agent platforms, never on the Mac. "This machine", a self-hosted environment of an agent platform where an agent could propose, is deferred ([product rulings](../../product/rulings.md)). Do not build a local runner, a helper or a process supervisor for it.
- **Swift 6 concurrency.** UI on the main actor, shared state behind actors, no data races, no force unwraps in app code. Structured `async`/`await`; no Grand Central Dispatch. Process and network I/O off the main actor.
- **Local data.** The app stores settings and caches only. No customer data, no holdout, no connector secret.
- **Distribution (decided 15 Nov).** A direct download, not the Mac App Store. Sign with a Developer ID, enable the hardened runtime and notarize. Updates use Sparkle ([libraries.md](../libraries.md)): serve the appcast and the update archives over HTTPS, and sign each archive with Sparkle's EdDSA (ed25519) key, with the public key in the app. Keep the EdDSA private key out of the repo and out of CI logs. Build and release steps are (target).
- **Updates (decided 15 Nov).**
  - **Signed feed.** Set `SURequireSignedFeed` so Sparkle also checks the EdDSA signature of the appcast and release notes; sign the release notes with `sign_update`. A compromised update server then cannot point users at another download.
  - **One feed, ours.** `SUFeedURL` is Antilog's appcast, for cloud and self-hosted customers alike. No per-server or mirrored feed: a rewritten feed would fail the signature check.
  - **Checks on by default.** Set `SUEnableAutomaticChecks` so the app checks daily without first asking. A person can turn checks off in the Settings window, as Sparkle's standard option; installing an update always shows the update window, so `SUAutomaticallyUpdate` stays off.
  - **Companies and air-gapped installs.** A company can turn update checks off for its Macs through device management and deploy each signed, notarized release itself. That is the path for a server that cannot reach the internet: nothing in the app needs to reach our feed.
  - **How a company turns checks off (target).** Do not rely on a configuration profile setting Sparkle's own keys. The app reads one managed preference of ours from `UserDefaults`; when a profile sets it, the app sets Sparkle's `automaticallyChecksForUpdates` to false at launch and shows the Settings toggle as off and locked (`UserDefaults.objectIsForced(forKey:)`), with a line saying the organization manages updates. Test it on a Mac with a profile installed before the first release.
  - **Not App Store sandboxed (target).** The app is a direct download and does not carry the `com.apple.security.app-sandbox` entitlement. Release CI checks it with `codesign -d --entitlements` and fails if the entitlement appears, until the owner rules on the Mac as "This machine".

## Working rules

- Prefer value types, explicit states, narrow access, and typed errors. Keep logic out of views and view bodies cheap and descriptive.
- Keep UI and framework state on `@MainActor`; protect shared mutable state with actors. Check cancellation in long work.
- One source of truth. Views own state with `@State` (private), edit borrowed state through `@Binding` or `@Bindable`, and receive plain values when they only read. Shared models are `@Observable` and `@MainActor`.
- Stable identity in dynamic collections (use the server's id). Keep every control keyboard reachable and accessible, support Dynamic Type, Increase Contrast and Reduce Motion, and take every visible string from the catalogue (localisable).
- A view's `body` runs often and on the main thread: no formatting of large data, sorting, parsing or I/O in it. Compute in the model and pass the result in.
- Async work started by a view uses `.task` (or `.task(id:)`), which cancels when the view leaves; check `Task.isCancelled` or use cancellable APIs in long loops, and do not write results to a model after cancellation.
- A user-triggered failure is shown (an alert or inline state), not logged and swallowed.

## Common diagnostics

- `Main actor-isolated ... from a nonisolated context`: isolate the caller or hop to the actor with `await`.
- `Sending 'x' risks causing data races`: make the transferred value `Sendable` or keep it within one actor.
- A slow type-check diagnostic: split the expression or extract a view struct.
- A source file added but "cannot find in scope": the file is not in the target; fix membership (or regenerate the project if it is generated).
- A `Process` that never exits or leaks: you did not read its output pipe, or did not terminate it on quit; handle both.
- Keychain `errSecMissingEntitlement` or `errSecInteractionNotAllowed`: the app lacks the right access group or the item's accessibility class does not allow background reads.

See [compiler and concurrency diagnostics](general/diagnostics.md) for more. For performance work, measure the same action before and after on a Release build; the workflow is in [performance](general/performance.md).

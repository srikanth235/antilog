# The runner

Where an agent runs (built, with the container backend; a real code host is not). The decisions are in [docs/V0.md](../../../docs/V0.md), the interfaces in [docs/V0-contracts.md](../../../docs/V0-contracts.md).

## The queue

Each session has a machine row (`machines`): `queued`, `claimed`, `running`, `idle`, `released`, `done` or `failed`. `session::start` queues it with the repos and environment it asked for, and its first words as a command. A runner polls `POST /runner/poll` with the runner key (`ANTILOG_RUNNER_KEY`, compared in constant time). Each poll renews every lease the runner holds (60 seconds), claims new work up to its capacity and returns the commands for its sessions. A lapsed lease puts the session back in `queued`; its unfinished commands are sent again and the old runner is told in `lost` to stop. A session that is Done or Failed is never claimed.

- `claimed`: leased, not yet started. `running` and `idle` follow OpenCode's busy and idle status. `released`: the runner exported the session and let the machine go; a person's message queues it again with `resume`.
- A claim returns the session spec: repos, the environment version the session started on (`EnvironmentSpec`: network, hosts, variables, setup script, default repos, size; the repos in the claim already include the environment's defaults), the latest version of every organization skill with its download path, the generated OpenCode config, the model, and three tokens (`Model`, `Mcp`, `Runner`) minted for the claim. Claiming revokes the tokens of any earlier holder; releasing revokes all of them.
- Per-session calls (`/events`, `/changes`, `/release`, `/export`, the skills download) carry that session's `Runner` token. None of the `/runner/*` routes is in the public OpenAPI.
- **One organization per runner.** A runner locks to the organization of the first session it claims (`runner_locks`, taken inside `claim_machines`, so the server enforces it) and is offered only that organization's sessions until it exits. A poll with no room (`capacity` 0) locks nothing. A runner's last poll carries `exiting: true`, which deletes the lock unless the runner still holds a session; A runner's lock records its last poll; one whose runner has not polled for 10 minutes (`RUNNER_LOCK_LAPSE_MS`, checked on the server's clock inside `claim_machines`) lapses, and any runner of any organization may take that name. Its leased sessions are requeued by the ordinary lease expiry, which is a minute, long before. A host is never shared between customers.
- **Limits on the machine.** (1) The runner lock lapses as above. (2) `--disk-gb` (env `ANTILOG_DISK_GB`, default 20, 0 for none) puts `--storage-opt size=` on each container; `probe_disk` asks `docker info` once at start and only devicemapper, btrfs, zfs, overlay2 on XFS pass, otherwise the runner logs once that the disk is not limited. A Docker that still refuses it (XFS without project quotas) drops the limit for that runner and the session starts without it. (3) A claim may hold a machine for `Settings.max_lifetime` (24 hours; `ANTILOG_MAX_SESSION_HOURS` on the server). The poll after that sends a `release` command with outcome `idle` (once per claim, `machines.expiring`), puts the session in Waiting for you and records an agent line that says why; the export is kept, and a person's message resumes it with a fresh 24 hours. (4) An organization has `max_running_sessions` (default 10, `PUT /organization/limits`, owners, audited as `organization.set_limits`; omitted leaves it as it is). `claim_machines` hands out no claim beyond it, counting `claimed`, `running` and `idle` machines, and locks the organization row so two runners cannot take the last place; a runner with no lock takes the first queued session of an organization that has room.
- The routes are mounted only when `ANTILOG_RUNNER_KEY` is set. `ANTILOG_MODEL` (`provider/model`) is required with it; `ANTILOG_PROXY_URL`, `ANTILOG_PUBLIC_URL`, `ANTILOG_CLONE_BASE` tell the machine where things are.

## `antilog runner`

Polls over outbound HTTPS only. A claim becomes one **machine**, started by a `Sandbox` (`runner/sandbox.rs`): `start` makes the machine, and the `Machine` it returns can `exec` a command, `put` a file as root, `spawn` a process that stays up, give a `listener` for a server, and `stop`, which takes the machine and its disk away. Everything the runner does to a session goes through those calls: the clones, the managed config, the skill packs and OpenCode (`Opencode::serve`, `export`, `import` in `opencode.rs`). A microVM or VM backend is another `Sandbox`; nothing else changes. `SandboxSpec` is the claim's `SessionSpec.environment` (CPU and memory, network level, variables, setup script) and nothing else; the session's `Model` token is the machine's login at the proxy.

In the machine the runner clones the repos into `/work/<repo>`, writes the config to `/etc/opencode/opencode.json` (OpenCode's managed path: a repo's own `opencode.json` cannot override it, and `OPENCODE_CONFIG` does not win, so never rely on it), writes the skill packs (JSON: text files with relative paths; a path that leaves the pack's folder skips the pack) into `/opt/antilog/skills/<name>/`, then starts `opencode serve` with a random password, `OPENCODE_DISABLE_MODELS_FETCH=1` and `autoupdate: false`. One session per machine: the managed config is one file.

### The container backend

`runner/container.rs` drives the `docker` command line through `tokio::process` (no Docker crate). `antilog runner --image antilog-session:latest --proxy host:port` (`ANTILOG_PROXY_ADDR`; `--docker`, `--setup-timeout-sec`).

- **Image.** `session-image/Dockerfile`: OpenCode pinned (build argument `OPENCODE_VERSION`, 1.19.6), git, and Docker. No OpenTofu, Terraform or cloud tool: the agent installs what a goal needs.
- **One container per session**, named `antilog-<session>`, with `--cpus`, `--memory` and `--memory-swap` from the environment (default 2 vCPU, 8 GB), `--pids-limit 4096` and a disk limit (`--disk-gb`, see Limits on the machine). Never `--privileged`.
- **Network.** Each session has its own `--internal` Docker network, which has no route out. The runner binds a relay on that network's gateway address that carries raw TCP to the proxy (`--proxy`, plain TCP: a proxy behind a TLS terminator needs its plain listener here). `HTTPS_PROXY` and `HTTP_PROXY` name the relay, with the CONNECT login `antilog:<model token>`. What passes is the proxy's call: the environment's hosts, or only the model gateway at `NetworkLevel::None`. The MCP endpoint and the code host reach the machine the same way, so the proxy must allow them.
- **Docker for the agent.** When the host's Docker has the `sysbox-runc` runtime, the container runs under it and a `dockerd` starts inside, with the proxy's variables, so the agent has its own Docker without `--privileged`. Without sysbox the container has no Docker daemon and the runner logs it. Rootless Docker in a plain container needs `--privileged` or the host's seccomp, AppArmor and `/proc` protections switched off, so it is not used.
- **Secrets stay out of the process list.** A variable or the proxy login reaches `docker` through its own environment (`-e NAME`), never as an argument.
- **A session's environment changes while it runs.** `Command::ApplyEnvironment` carries the new `EnvironmentSpec`. The container starts with `BASH_ENV=/etc/antilog/env.sh` (the proxy's own pair, so an environment cannot set it); `prepare` writes the file and `Live::apply_environment` rewrites it: `unset` for each name the new version dropped, `export NAME='value'` for each one it has. New non-interactive bash processes (the agent's commands) source it; OpenCode's own process, a login shell and other shells keep the old environment until the machine next starts. A setup script that differs from the one the machine runs, and is not empty, runs now through the same `run_script` as at the start (with the new variables, as root, from the work folder, under `--setup-timeout-sec`) and never touches the start marker; a failure is a note and the heads-up line, not the session's end. The network needs nothing here: the proxy reads the session's version on every tunnel.
- **Setup scripts.** The container is always the session image, started with the environment's variables set. `prepare` in `runner/session.rs` clones the repos, then `run_setup` runs the script as root with the work folder (the one that holds the checkouts, each repo a subfolder) as its working directory: `timeout -k 10 <limit> bash -c <script>` with stderr folded into stdout, once per container (a marker file, `.antilog-setup`, in the work folder). A non-zero exit, and a timeout (`--setup-timeout-sec`, 600 by default; exit 124), are the same: the session starts without it, an `Item::Note` goes to the transcript with the exit code and the last 2 KB of output (each repo's clone credential replaced by `***`), and one line ("[Antilog] The environment's setup script failed, so tools it installs may be missing.") is put ahead of the first message the agent is sent. There is no setup image and no snapshot cache.
- **Release.** `opencode export` goes to the server, then `docker rm -f -v` removes the container and its disk, the network goes, and the relay stops. A session that fails to start is cleaned up the same way.

### Leaving

`--exit-after-last-session` makes the runner exit once its last session is let go, so its host can be wiped. `--drain-grace-sec` (default 30) follows Claude Code's drain: on SIGTERM or SIGINT, or after the last session with that flag, the runner **drains**: it claims nothing new, keeps polling to hold its leases and deliver commands, and waits up to the grace for its sessions to be let go; after the grace it stops them (their leases lapse and the sessions queue for another runner). Then it sends its last poll (`exiting: true`) and exits.

- Messages go in with `prompt_async`, an abort with `abort`, a person's answer to a permission with `/permission/{id}/reply`.
- `GET /event` has no replay and no event id. After every connect the runner reads `GET /session/{id}/message` (paged by `before`, cursor in `x-next-cursor`), `GET /permission` and `GET /session/status`, and sends what is new, keyed by message id and part id. Only what an agent finished saying and each finished tool call are sent (a call is sent when it ends, never while it runs: `session_events` is append-only). A tool call carries a `ToolRecord`: a label (the bash command's first line, the file path, the tool's name), `done` or `failed` (an `error` state, or a bash exit status other than 0), and its input and output, each cut to 4 KB with the Authorization header, bearer tokens and Antilog token forms (`alt_`, `als_`, `alc_`) replaced by `[redacted]`. The `antilog_*` tools are not sent: the server's MCP endpoint records each call itself, with the same record, so the conversation shows it once.
- A `permission.asked` event becomes an Ask first card (`ask_first`, always asks unless policy allows). The answer comes back as an `approval` command.
- Release: `opencode export` goes to the server with the release. A later claim fetches it and runs `opencode import`, so the agent has its history. If the stream cannot be kept the session is released as failed.
- The runner key is never in a machine: the plain backend removes it from what it starts, and a container never receives it.

## What a repo can still do

Run against OpenCode 1.19.6 with the managed config in place:

| | repo `opencode.json` provider, permission, autoupdate | repo MCP servers, skills, agents | repo plugin code |
| --- | --- | --- | --- |
| default | cannot override | loaded | runs |
| `--pure` | cannot override | loaded | does not run |
| `OPENCODE_DISABLE_PROJECT_CONFIG=1` | cannot override | not loaded | not loaded |

`antilog runner --pure` and `--disable-project-config` set them; both are off by default because a repo may add its own tools inside the machine, as in Claude Code (`docs/V0-contracts.md`). A repo's plugin is code that runs next to the session's tokens: turn `--pure` on where that is not acceptable.

## Testing it

The plain-process backend (`sandbox::plain`, tests only: it isolates nothing) runs a "machine" in folders a test chooses; `runner/tests.rs` wraps it so that `opencode` is a fake HTTP server. The container backend is tested through a `Cli` that records the `docker` calls (`container.rs`), and its relay against a local socket; the store's lock in `runner_lock_suite` (the fake and Postgres). The ignored `real_opencode_runs_a_session_end_to_end` drives the pinned OpenCode against a scripted model server; its comment says how to run it. A real container run needs a Docker daemon and the built image, and was not run where this was written.

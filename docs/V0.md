# V0 design decisions

Owner decisions of 19–20 Nov 2026. The skills follow this page; where a board disagrees, this page wins.

## v0 is cloud sessions only

Owner, 21 Nov: v0 focuses only on cloud sessions, as Claude Code's. Experiments and the judge (seal, measure, trials, holdout, wins, receipts, value) are parked, not redesigned. Projects stay: a project groups sessions, as Claude Code's sidebar groups sessions under a project (owner, 21 Nov). A session belongs to one project and has its repos, environment, model and agent; the sidebar lists projects, each with its sessions under it. A spend cap comes from the organization (monthly cap) with an optional per-session cap. On the orchestrator's recommendation the parked code is deleted rather than hidden, as the build rule asks; the last commit that has it is `daa445f` on `claude/dreamy-ptolemy-vg7uga`, to restore from when the judge returns (the iteration ideas of 21 Nov: a draft stage, diff-based versions, trials that carry across versions, k counted across the experiment, a minimal seal input, a version timeline). Where a decision below names experiments or the judge, it waits with them.

## Sessions copy Claude Code cloud sessions

- **Runner polls a queue.** The server keeps one queue of sessions. An `antilog runner` on any host polls it over outbound HTTPS, claims a session with a lease, clones the repos into the session's machine, starts the harness there and streams its events back. Nothing connects inward. This replaces the `Platform` trait, the stepping relay and every agent-platform adapter (AgentCore, Claude Managed Agents, the OpenAI Agents API, Foundry, Google Agent Runtime).
- **One machine per session, on hosts we keep.** In v0 runners live on a small pool of hosts; the repo has no code that creates hosts, and an agent sets the pool up on demand. A runner locks to one organization when it claims its first session and serves only that organization until it exits, so customers never share a host (as Claude Code's self-hosted runner locks to one owner). Each session runs in its own container on the host, with Docker available inside it, behind a small `Sandbox` trait in the runner so that a microVM or VM backend can replace containers later without touching anything else. Default 2 vCPU and 4–8 GB per session; idle sessions are released and their disk dropped; a maximum lifetime and a cap on concurrent sessions per organization apply (owner, 20 Nov).
- **OpenCode is the harness.** The only one in v0, pinned to one version in the session image. The runner writes OpenCode's machine-wide config (provider, the `antilog` MCP entry, permissions, skills folders), which a repo cannot override, and drives it over its HTTP API. Other harnesses come later through the same runner.
- **Environments.** As Claude Code's "Edit cloud environment": a name, default repositories, a network level (none, limited with allowed hosts, full), network secrets, a setup script and plain variables, with a machine size. In v0 a service key (not a model key) goes in a plain variable, which the agent can read; the screen says so. A network secret is stored sealed and write-only; the proxy adding it to requests is a target (see the decisions of 21 Nov, environments). A fresh container starts with the variables set, the session's repos are cloned, the setup script runs as root from the folder that holds the checkouts, then OpenCode starts. A failing script does not fail the session.

## The proxy

One proxy outside the session machine does two jobs in v0:

1. **Model gateway.** The customer brings their model keys, saved per organization per provider and never sent into a session. The harness's base URL points at the proxy, which swaps the session's short-lived token for the real key, forwards without translation, books spend from each response's token counts and refuses calls once the session's, the project's or the organization's budget is spent.
2. **Network allowlist** for the session's outbound traffic, without decrypting it.

## What the agent can reach

- **One MCP endpoint per session**, served by our server: the setup tools (`attach_repo`, `request_credential`, `set_environment`, `request_budget`) plus the tools of every organization connector. Connector credentials stay on the server. Each connector tool is on, off or ask first (an approval card).
- **Skills** are organization skills with fixed versions, in `SKILL.md` folders. The runner copies the latest version of every organization skill into OpenCode's skills folder when it claims the session.
- **Plugins** are an Antilog bundle (skills and connectors). Adding one unpacks it into those parts, each governed as usual. Harness-native plugins are later.

## Testing

The agent runs tests inside the session's own machine, as in any cloud session. (Parked with the judge: the sealed test command, whose number the judge took instead of the agent's report.)

## No infrastructure tool in the product

The product has no OpenTofu (or Terraform, Pulumi, CloudFormation) concept: no sealed templates, no state it keeps, no module per cloud for customers. When a goal needs infrastructure, the agent writes the files and runs the tool itself inside the session's machine, as it would any other code, with credentials from the environment. The same holds for hosting Antilog cloud itself: the repo has no infrastructure code and no Lambda. The server and the proxy are plain binaries that run anywhere; an agent writes and runs whatever deploys them, on demand (owner, 20 Nov).

## Decisions taken on the orchestrator's recommendation
- **Terminal (owner, 21 Nov):** the session's Terminal tab uses OpenCode's PTY API in the machine; the runner opens an outbound WebSocket per terminal and the server relays it to the browser, so nothing connects inward. The web app renders it with xterm.js (new dependency, approved by the owner). Editors and owners only; opening one is audited, keystrokes are not recorded.
- **Model picker (owner, 21 Nov):** copies Claude Code's composer menu: favourite models with number keys, Effort submenu (OpenCode model variants), More models (searchable, by provider). No fast mode until a provider offers one.

The owner lets the orchestrator decide where it has a recommendation, without pausing, as long as each decision is written here (owner, 20 Nov). The owner can reverse any line.

- **Environments (E):** variable names `ANTILOG_*` and the `*_PROXY` names are refused; an environment's id comes from its name, so names are unique; sizes are 1 to 16 CPUs and 1 to 64 GiB; the built-in `default` is listed first and its id is reserved; a session whose environment cannot be read gets no network. A session may later move to another version (see the decisions of 21 Nov for changing a running session).
- **Platform hosts:** the proxy allows the hosts in `ANTILOG_PROXY_PLATFORM_HOSTS` (the proxy's and the server's public names and the code host) at every network level, so a session at `none` still reaches its model, MCP and git.
- **Runner lock expiry:** a runner's organization lock lapses when the runner has not polled for 10 minutes, so a crashed runner does not hold its organization forever.
- **Session machine limits:** a disk limit per container (20 GiB, where the storage driver supports it), a maximum lifetime per claim (24 hours, then the machine stops, the session waits for a person and a message resumes it), and a cap on running sessions per organization (10 by default, idle machines count, set through `PUT /organization/limits`).
- **Docker for the agent:** only under the sysbox runtime, never `--privileged`; without sysbox the agent has no Docker.
- **Drain:** a stopping runner claims nothing new, waits `--drain-grace-sec`, stops what is left, then exits.
- **Holdout runs in a fresh machine (parked with the judge):** a measurement on holdout data never runs in the agent's live machine. The runner starts a second container from the same environment version through the same `Sandbox`, checks out the commits, runs the sealed command with the holdout data, and removes the container. Only that container receives the holdout data or its credential. Measurements on evaluation data stay in the session machine. This is the same kind of machine, not a separate judge sandbox.
- **Holdout machine details (parked with the judge):** the fresh machine clones the commits from the code host, so nothing the agent left in its own machine decides the run; a trial commit must therefore be pushed before its holdout run, which the code host work owes. It uses the session's proxy login and is not counted as a session. At start the runner removes any holdout container or network an earlier run left (one runner per host).
- **Bash runs without asking** in the session machine, as in Claude Code cloud sessions: the machine is isolated and reaches out only through the proxy. Edits were already allowed.
- **A decided card reaches the agent at once:** its outcome ("Approved: ...", "Declined: ...") is sent into the session as a message from Antilog, which wakes the agent. An approved repo is cloned into the live machine before that message.
- **OpenCode Go is its own provider (21 Nov), taken on the orchestrator's recommendation.** `ModelProvider::OpencodeGo`, wire and route name `opencode-go`, key `PUT /model-keys/opencode-go`, route `/opencode-go/v1` to `ANTILOG_PROXY_OPENCODE_GO_URL` (default `https://opencode.ai/zen/go`), and its own hourly price table from `<upstream>/v1/models`; `/opencode` stays Zen (default `https://opencode.ai/zen`). A session model is `opencode-go/<model>`. OpenCode 1.19.6 already knows `opencode-go` (34 models in its snapshot, `@ai-sdk/openai-compatible`, its own upstream URL), so the generated config only needs to override the base URL and key; it also names `npm` and `name` so it works if the snapshot ever lacks the provider. A model newer than the snapshot is unknown to OpenCode until the pin moves. The model picker is free text in v0 (no list endpoint), so "list Go models when a Go key is set" is not built: the hint names the prefix and a model list is a product call for the owner. Go is a subscription, so the spend Antilog shows is at Go's list prices, as the Settings row says. Booking at list price keeps the budget caps honest, but is not the bill.
- **OpenCode Zen prices come from Zen's own model list,** fetched without a key and refreshed hourly; time-of-day surcharges are ignored in v0.
- **Platform boards deleted:** `SettingsPlatforms*`, `AddPlatform` and `PlatformError` are gone; the Agents boards point at Model keys instead.

Decisions of 21 Nov for cloud sessions only (the owner's section above), taken on the orchestrator's recommendation:

- **Parked code is deleted.** Experiments, the judge (seal, measure, history, deliver, watch), trials, measurements, holdout, wins, receipts, value models, evaluations, datasets, the report and value pages are gone from the code. `daa445f` restores them.
- **Session shape.** A session belongs to a project in an organization and has `id`, `projectId`, `title`, `createdBy`, `agent`, `model`, `repos`, `environment` with its version (pinned at start), an optional `budgetCapCents`, `followPolicy`, `status` (working, waiting_for_you, done, failed) and `note`. The title is the first line of the prompt, up to 80 characters, when none is given. `auto` resolves to the owner's default agent. The model is `provider/model` from the request, else the server's `ANTILOG_MODEL`. `followPolicy` (the composer's Mode) stays on the session.
- **Budgets nest.** A session's own optional cap is at most its project's monthly cap, which is at most the organization's monthly cap (409 `over_cap`, both ways). A new session's cap defaults to the project's `defaultBudgetCents`, then the organization's. The proxy's check (`budget::ensure_room`) looks at the session cap, then the project's, then the organization's, and refuses with 402 in the provider's own error shape. `request_budget` works only for a session with its own cap (otherwise it says so and points to Settings); an approved Raise budget card raises that session's cap.
- **Routes.** `POST /projects/{id}/sessions` starts a session, `GET /projects/{id}/sessions` lists a project's (newest first, `?mine=true`), `GET /sessions` lists the organization's across projects (`?mine=true`). `/experiments*`, `/evaluations*`, `/trials/*`, the value and report routes, `/spend`, `/tools`, the code-host webhook, `/runner/sessions/{id}/results` and `POST /sessions` are gone.
- **Roles are unchanged:** an organization role (viewer, editor, owner) with a per-project override. In a project any editor may message or stop any session of it; viewers read. Creating a project is an organization-owner action; project owners set the project's limits and roles.
- **Every session gets all connectors and the latest skills.** No per-session selection and no project skill switch. Removing a skill, connector or plugin part is no longer blocked by "in use".
- **`antilog mcp` and the REST tool endpoints are removed.** The CLI is `antilog runner` only; a session's agent reaches Antilog through `/mcp/sessions/{id}`.
- **The code host is removed:** the `CodeHost` trait, its webhook and the pull-request tables. A pull request comes later, from the agent with the repo's credentials.
- **Cards that stay:** raise_budget, add_credential, attach_repo, change_environment, ask_first, use_connector_tool, each with per-kind policy. Removed: seal_experiment, open_pull_request, keep_going, continue_on_another_agent, and the value-model approvals.
- **The holdout path is removed from the runner:** `Command::Run`, `RunSpec`, `RunResult`, `SessionMachine`, `QueueMachine`, the runner's `machine.rs`, `RUN_LABEL` and the sweep. Spend kinds are tokens and machine.
- **The migration clears the session area.** `20261121000000_cloud_sessions_only.sql` drops the judge tables, experiments, evaluation templates, per-experiment selections and project skill switches, keeps projects, project roles and limits, empties sessions (there are no customers) and adds the session columns above.
- **Plugins are skills and connectors;** evaluation templates are dropped.
- **Live events carry no experiment id:** `hello`, `resync`, `message`, `session` and `cards`.
- **Advisory ignore removed:** a stale `deny.toml` ignore for a `chrono` advisory is gone.

Decisions of 21 Nov for environments, taken on the orchestrator's recommendation (the owner asked for Claude Code's cloud environments):

- **Start order.** A fresh container is started with the environment's variables set (`-e`), the session's repos are cloned into the work folder, the setup script runs as root with that folder as its working directory (each repo is a subfolder named after it), then OpenCode starts. A machine that is started again in the same container does not run it again (a marker file in the work folder). A released session gets a new container, so the script runs again there.
- **No snapshot image.** The per-version setup image (`antilog-env:<id>-v<version>`, its 7 day expiry and `--state-dir`) is deleted. A cache keyed by environment, version and the repos' commit shas would save minutes only for a second session on the same host with the same commits, and costs a store, a key and an expiry; a plain run of the script is simpler and correct. It can come back as a pure cache.
- **A failing script does not fail the session.** The script runs with `timeout` (10 minutes by default, `antilog runner --setup-timeout-sec`); a non-zero exit and a timeout are treated the same. The session starts without it; the runner sends a note into the transcript (kept as an Antilog note, an agent-kind event like the machine-time and card notes, so no new event kind) with the exit code (124 for a timeout) and the last 2 KB of output with each repo's clone credential taken out, and puts one line ("[Antilog] The environment's setup script failed, so tools it installs may be missing.") ahead of the first message the agent is sent. The agent's own context for a failure is that line; the full note is for the person.
- **Default repositories.** An environment version holds a list of `owner/repo` (at most 50). A new session that names an environment starts with those repos first, then the ones the person picked, without repeats; the seed and the session record the merged list. A change is a new version, as the other fields are. `EnvironmentSpec.repos` carries them to the runner for information; the claim's `repos` already include them.
- **Network secrets are data, not yet injection.** Per environment version: a list of host, header name, optional prefix and a sealed value (XChaCha20-Poly1305 under the row `env_secret:<org>:<id>:<host>:<header>`, so a later version without a new value copies the sealed value of the one before). Values are write-only: the API takes `value` on create and edit and never returns one (an edit that leaves it out keeps the stored value); the runner never receives one. Injection (the proxy terminating TLS for those hosts only, with a CA the machine trusts and per-host certificates) is more than a small change to a CONNECT proxy, so it is marked "(target)" and the edit dialog says the values are kept but not yet applied. Nothing reads the values yet except a store call the proxy will use.
- **The edit dialog** is a dialog on Settings, Connections (boards `SettingsEnvironment` and `SettingsEnvironmentSecrets`): Name, Repositories with + Add, then rows with a summary and a chevron (Network access, Network secrets, Setup script, Environment variables, Machine size) that open their editors in place, Archive environment at bottom left and Cancel and Save changes at right. Archive moves from the list into the dialog.

Fixes from the first end-to-end run through the web UI (21 Nov), taken on the orchestrator's recommendation:

- **Capacity is a flag.** `antilog runner --sessions N` (`ANTILOG_RUNNER_SESSIONS`) replaces the constant of one. The default is 4, cut to one per CPU and one per 2 GiB of memory on a smaller host; a value given is trusted. Each session has its own container, so OpenCode's one managed config file is no longer a reason for one.
- **An idle machine lets go.** After `--idle-timeout-sec` (default 600, 0 never) with the agent idle and no message, the runner exports the session and releases the machine as an `idle` release does; the session stays Waiting for you and a person's message resumes it. A message that races the decision is delivered after the next one wakes the machine (the second message resumes both); the queue is not changed for it.
- **Two more statuses.** `queued` is a session no runner holds (from its start, and from a message that wakes a released machine) until a runner claims it, then `working`; `stopped` is what a person stopped (it was Done with a note; migration `20261121600000_session_statuses.sql` renames old rows and teaches the queue's claim function and the final-state guard the new values). Both are in `SessionStatus` and the OpenAPI document. The sidebar and header show Queued with `st-draft` in `ink3` and Stopped with `st-stop` in `ink2`; Failed keeps `st-fail` in `bad` (board `DesignRules`).
- **A failure carries its reason.** `Release` has an optional `reason` (the error text, clone credentials and Antilog tokens replaced by `***`, 400 characters). The server keeps its first line as the session's note and records it in the transcript as an `error` event. This adds the event kind `error` (reversing "no new event kind" for notes, for errors only); the web shows it as a red note (`.fl` with `st-fail`) and the status line reads "The session failed: <reason>".
- **A refused model call is an error, not a message.** OpenCode's assistant message `error` and `session.error` become `Item::Error` (once per turn, with the provider's message and, when it adds to it, the words of the response body), shown in red. The session is Waiting for you with the error visible; it is Failed only when OpenCode gives up (stops answering, released as failed with a reason).
- **No card for the agent's own folders.** The managed config allows `external_directory` for `/work/**` and `/tmp/**`. Each ask OpenCode raises has a fresh id, so the same directory (another repo under `/work`, scratch space in `/tmp`) raised a new "Allow once" card every time; anything else still asks.
- **The session image has python3, pip and venv,** and its apt sources are https (ca-certificates first), so `apt` works through the proxy, which tunnels HTTPS only. The image was not built where this was written (no Docker daemon).
- **A card says what it costs once,** in its footer as the boards draw it; the duplicate "What it may cost" row is gone.
- **The Playwright model-key test counts rows from the page** (the "Add key" buttons) instead of a literal, so a new provider needs no edit. The environments test creates a project first, since the composer needs one.

- **Tool calls in the conversation (owner, 21 Nov):** the session page copies Claude Code's cloud UI. Consecutive tool calls between two messages fold into one muted group line ("Ran 19 commands (1 failed)", with "Edited N files", "Read N files", "Called <tool> N times" and, for mixed kinds, "Ran N steps"); the latest group is open and reads "Running… N commands" while the agent works. The server therefore stores, per tool call, a label, a status and its input and output cut to 4 KB with credentials removed; this reverses "store no tool output" for those 4 KB (whole output and raw logs stay in the machine). A call is recorded when it ends, so a running group is derived (it is the last block and the session is Working) and `session_events` stays append-only. The Antilog MCP tools are recorded by the server's endpoint with their input and answer, and the runner drops OpenCode's `antilog_*` copy, so each shows once under its Antilog name.
- **Overview panel (owner, 21 Nov):** the Details panel is now the Overview: Environment (name and repos), Spend (the session's own), Connectors and Outputs (files, patches, pull requests), each linking to its page. The API does not serve the branch, context use or outputs, so the web app leaves those rows out and the board draws them as the target.

- **Changes tab (owner, 21 Nov):** the session's Changes panel copies Claude Code's cloud diff view. At the end of every agent turn, and when the session is let go, the runner reads each repo of the machine against the commit it was cloned at (the base) and sends one report: up to 50 commits since (sha, subject, time), the files of `git diff <base>` through a copy of the index with untracked files added, so new files count and ignored files never do, and the files of each commit against its parent. The server keeps the latest report per session and repo (`session_changes`, `session_commit_changes`, replaced on each report) and serves `GET /sessions/{id}/changes` and `GET /sessions/{id}/changes/commits/{sha}` to anyone who may read the session; a `changes` live event tells an open tab to refetch. This reverses "the server stores no diff" for these reports (the owner's task of 21 Nov); the code stays out of the audit log and the conversation, and the Postgres rows are the Changes panel's view of the machine, replaced by the next report.
- **Changes details, on the orchestrator's recommendation:** per-commit diffs are stored (a released machine cannot answer later) rather than fetched by a second call to the runner; one file's patch is the unified diff with three lines of context (`-U3`), so the panel shows hunks and counts the unmodified lines between them but cannot expand them until the server sends fuller context; renames are shown as a removed and an added file (`--no-renames`); a binary file shows "Binary file not shown"; the caps are 2 MB of patch text for a repo's all-changes diff and 2 MB for its commit diffs together (past it a file keeps its counts, loses its patch and shows "Too large to show"), and a diff of more than 200,000 changed lines is sent without patches; the runner and the server both enforce the caps. The header always reads "base → head": the repo's current branch, or the short sha of HEAD when none is checked out (including "main → main" when the agent never left the base branch); a session with several repos picks one in the header. The Playwright flow tests do not cover session panels, so none was added.

Decisions of 21 Nov for changing a running session's environment (the owner's task: the agent's `set_environment` and a person's picker work, as Claude Code lets a session move to another environment or edit its own), taken on the orchestrator's recommendation:

- **What the tool takes.** `set_environment` proposes a concrete change: `network` (none, limited, full), `add_hosts` and `remove_hosts`, `set_variables` and `unset_variables`, `setup_script` (the whole text; empty removes it) and `add_repos` and `remove_repos`. The old `image` and `size` inputs are gone (there is no image per session, and a size applies only at a container's start, so a card for it could promise nothing). Names `ANTILOG_*` and the `*_PROXY` names, a host that is not an exact name, and hosts at a level other than limited are refused when the tool is called, before a card exists.
- **The card holds the whole proposal.** `CardPayload::ChangeEnvironment` carries the change as asked, the environment as the session runs it (`before`) and as it would be (`after`: network, hosts, variable names and values, script text, repos) and the two versions. A network secret never appears (a change cannot touch one; its value is write-only). Variables are plain by decision, so their values are on the card and in the stored payload. A card raised with the old payload loses its payload in migration `20261121400000`.
- **A change is the environment's own next version, and other sessions see it.** Approving makes version N+1 of the session's environment, built on the newest version (not the version the session started on, so another person's edit made since is kept, and the card says so), then moves the session to it. Other sessions on that environment get it when they start, and the card says so. "Only this session" (a fork of the environment for one session) is out of scope; a person can make a new environment in Settings and move the session to it.
- **The built-in default cannot change,** so a session on it gets a new environment of its own, "Session <first 8 characters of its id>", seeded from the default plus the change, and moves to it; the card says so. Archived environments take no change.
- **The proxy reads the session's version on every tunnel.** Which version a session is on is read from its machine row (a small query) and what a version allows is kept for good in memory, since a version never changes. The 60-second cache is gone: it could not be invalidated across the server and proxy processes without a message channel, and this needs none. A change to the network, hosts or registries therefore applies on the next CONNECT. A tunnel already open stays open.
- **Variables for new processes through `BASH_ENV`.** The container starts with `BASH_ENV=/etc/antilog/env.sh` (the proxy's own pair, which an environment cannot override), a file the runner writes at start and rewrites on a change: `unset` for each name the new version dropped, `export` (single-quoted, so a value is taken verbatim) for each one it has. Every new non-interactive bash, which is how the agent's commands run, sources it. OpenCode's own process keeps the environment it started with until the machine next starts (restarting its server would end the turn that waits for the approval); a login shell or a non-bash shell does not read the file. This was tested with a real `bash` in the runner's tests.
- **The setup script runs now if it changed.** `Command::ApplyEnvironment` carries the new `EnvironmentSpec`. The runner runs a changed, non-empty script as root from the work folder, under the same `timeout`, with the new variables, and never marks the container's start marker. A failure or timeout is a note in the transcript and the "[Antilog] The environment's setup script failed" line ahead of the next message, as at the start, and never fails the session. The command is queued before the outcome message, so the runner finishes the script before the agent reads that the change is approved.
- **A person moves a session too.** `PUT /sessions/{id}/environment` takes an environment id (`default` for the built-in one), moves the session to its newest version, adds its default repos (cloned now into a running machine) and tells the agent in a message and an Antilog note. Editors and owners of the project (`session.set_environment`, in the permission matrix, a denial audited). The Overview's Environment row has Change (the picker, a board `SessionEnvironment`) and Edit (the environment's edit dialog, which makes its next version). The card has its own board `SessionEnvironmentCard`.
- **What a stopped machine does.** The same code path moves the session record and its machine seed together (`SessionStore::set_session_environment`, one transaction); a machine no runner holds gets no command, and its next claim reads the new version, so the variables and script apply then and the card says so.
- **Audit and policy.** A change writes `environment.edit` (or `environment.create` for the default's new environment) and `session.set_environment`, by whoever approved, or by Antilog when policy did. The card kind keeps its policy default (Always ask) and may be pre-approved like the others.
- **Cards of other kinds are unchanged.** The model-key code is untouched.

## Not in v0

Experiments and the judge (parked, `daa445f`), a pull request opened by Antilog (the agent opens it with the repo's credentials), nested sessions, throwaway cloud environments for testing, harnesses other than OpenCode, translating between model formats, harness-native plugins, Kubernetes and Helm as a requirement.

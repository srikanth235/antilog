# V0 design decisions

Owner decisions of 19–20 Nov 2026. The skills follow this page; where a board disagrees, this page wins.

## v0 is cloud sessions only

Owner, 21 Nov: v0 focuses only on cloud sessions, as Claude Code's. Experiments and the judge (seal, measure, trials, holdout, wins, receipts, value) are parked, not redesigned. Projects stay: a project groups sessions, as Claude Code's sidebar groups sessions under a project (owner, 21 Nov). A session belongs to one project and has its repos, environment, model and agent; the sidebar lists projects, each with its sessions under it. A spend cap comes from the organization (monthly cap) with an optional per-session cap. On the orchestrator's recommendation the parked code is deleted rather than hidden, as the build rule asks; the last commit that has it is `daa445f` on `claude/dreamy-ptolemy-vg7uga`, to restore from when the judge returns (the iteration ideas of 21 Nov: a draft stage, diff-based versions, trials that carry across versions, k counted across the experiment, a minimal seal input, a version timeline). Where a decision below names experiments or the judge, it waits with them.

## Sessions copy Claude Code cloud sessions

- **Runner polls a queue.** The server keeps one queue of sessions. An `antilog runner` on any host polls it over outbound HTTPS, claims a session with a lease, clones the repos into the session's machine, starts the harness there and streams its events back. Nothing connects inward. This replaces the `Platform` trait, the stepping relay and every agent-platform adapter (AgentCore, Claude Managed Agents, the OpenAI Agents API, Foundry, Google Agent Runtime).
- **One machine per session, on hosts we keep.** In v0 runners live on a small pool of hosts; the repo has no code that creates hosts, and an agent sets the pool up on demand. A runner locks to one organization when it claims its first session and serves only that organization until it exits, so customers never share a host (as Claude Code's self-hosted runner locks to one owner). Each session runs in its own container on the host, with Docker available inside it, behind a small `Sandbox` trait in the runner so that a microVM or VM backend can replace containers later without touching anything else. Default 2 vCPU and 4–8 GB per session; idle sessions are released and their disk dropped; a maximum lifetime and a cap on concurrent sessions per organization apply (owner, 20 Nov).
- **OpenCode is the harness.** The only one in v0, pinned to one version in the session image. The runner writes OpenCode's machine-wide config (provider, the `antilog` MCP entry, permissions, skills folders), which a repo cannot override, and drives it over its HTTP API. Other harnesses come later through the same runner.
- **Environments.** A network level (none, limited with allowed hosts, full), plain variables and a setup script. In v0 a service key (not a model key) goes in a plain variable, which the agent can read; the screen says so. Network secrets that the proxy attaches without the key entering the machine come after v0. The setup result is snapshotted and reused; a snapshot expires after 7 days unused.

## The proxy

One proxy outside the session machine does two jobs in v0:

1. **Model gateway.** The customer brings their model keys, saved per organization per provider and never sent into a session. The harness's base URL points at the proxy, which swaps the session's short-lived token for the real key, forwards without translation, books spend from each response's token counts and refuses calls once the session's, the project's or the organization's budget is spent.
2. **Network allowlist** for the session's outbound traffic, without decrypting it.

## What the agent can reach

- **One MCP endpoint per session**, served by our server: the setup tools (`attach_repo`, `request_credential`, `set_environment`, `request_budget`) plus the tools of every organization connector. Connector credentials stay on the server. Each connector tool is on, off or ask first (an approval card).
- **Skills** are organization skills with fixed versions, in `SKILL.md` folders. The runner copies the latest version of every organization skill into OpenCode's skills folder when it claims the session.
- **Plugins** are an Antilog bundle (skills and connectors). Adding one unpacks it into those parts, each governed as usual. Harness-native plugins are later.

## Testing

The agent runs tests inside the session's own machine, as in any cloud session. (Parked with the judge: the sealed test command, whose number the judge took instead of the agent's report.)

## No infrastructure tool in the product

The product has no OpenTofu (or Terraform, Pulumi, CloudFormation) concept: no sealed templates, no state it keeps, no module per cloud for customers. When a goal needs infrastructure, the agent writes the files and runs the tool itself inside the session's machine, as it would any other code, with credentials from the environment. The same holds for hosting Antilog cloud itself: the repo has no infrastructure code and no Lambda. The server and the proxy are plain binaries that run anywhere; an agent writes and runs whatever deploys them, on demand (owner, 20 Nov).

## Decisions taken on the orchestrator's recommendation

The owner lets the orchestrator decide where it has a recommendation, without pausing, as long as each decision is written here (owner, 20 Nov). The owner can reverse any line.

- **Environments (E):** variable names `ANTILOG_*` and the `*_PROXY` names are refused; an environment's id comes from its name, so names are unique; sizes are 1 to 16 CPUs and 1 to 64 GiB; the built-in `default` is listed first and its id is reserved; a session whose environment cannot be read gets no network.
- **Platform hosts:** the proxy allows the hosts in `ANTILOG_PROXY_PLATFORM_HOSTS` (the proxy's and the server's public names and the code host) at every network level, so a session at `none` still reaches its model, MCP and git.
- **Runner lock expiry:** a runner's organization lock lapses when the runner has not polled for 10 minutes, so a crashed runner does not hold its organization forever.
- **Session machine limits:** a disk limit per container (20 GiB, where the storage driver supports it), a maximum lifetime per claim (24 hours, then the machine stops, the session waits for a person and a message resumes it), and a cap on running sessions per organization (10 by default, idle machines count, set through `PUT /organization/limits`).
- **Docker for the agent:** only under the sysbox runtime, never `--privileged`; without sysbox the agent has no Docker.
- **Drain:** a stopping runner claims nothing new, waits `--drain-grace-sec`, stops what is left, then exits.
- **Holdout runs in a fresh machine (parked with the judge):** a measurement on holdout data never runs in the agent's live machine. The runner starts a second container from the same environment version through the same `Sandbox`, checks out the commits, runs the sealed command with the holdout data, and removes the container. Only that container receives the holdout data or its credential. Measurements on evaluation data stay in the session machine. This is the same kind of machine, not a separate judge sandbox.
- **Holdout machine details (parked with the judge):** the fresh machine clones the commits from the code host, so nothing the agent left in its own machine decides the run; a trial commit must therefore be pushed before its holdout run, which the code host work owes. It uses the session's proxy login and is not counted as a session. At start the runner removes any holdout container or network an earlier run left (one runner per host).
- **Bash runs without asking** in the session machine, as in Claude Code cloud sessions: the machine is isolated and reaches out only through the proxy. Edits were already allowed.
- **A decided card reaches the agent at once:** its outcome ("Approved: ...", "Declined: ...") is sent into the session as a message from Antilog, which wakes the agent. An approved repo is cloned into the live machine before that message.
- **OpenCode Zen prices come from Zen's own model list,** fetched without a key and refreshed hourly; time-of-day surcharges are ignored in v0.
- **Platform boards deleted:** `SettingsPlatforms*`, `AddPlatform` and `PlatformError` are gone; the Agents boards point at Model keys instead.

Decisions of 21 Nov for cloud sessions only (the owner's section above), taken on the orchestrator's recommendation:

- **Parked code is deleted.** Experiments, the judge (seal, measure, history, deliver, watch), trials, measurements, holdout, wins, receipts, value models, evaluations, datasets, the report and value pages are gone from the code. `daa445f` restores them.
- **Session shape.** A session belongs to a project in an organization and has `id`, `projectId`, `title`, `createdBy`, `agent`, `model`, `repos`, `environment` with its version (pinned at start), an optional `budgetCapCents`, `followPolicy`, `status` (working, waiting_for_you, done, failed) and `note`. The title is the first line of the prompt, up to 80 characters, when none is given. `auto` resolves to the owner's default agent. The model is `provider/model` from the request, else the server's `ANTILOG_MODEL`. `followPolicy` (the composer's Mode) stays on the session.
- **Budgets nest.** A session's own optional cap is at most its project's monthly cap, which is at most the organization's monthly cap (409 `over_cap`, both ways). A new session's cap defaults to the project's `defaultBudgetCents`, then the organization's. The proxy's check (`budget::ensure_room`) looks at the session cap, then the project's, then the organization's, and refuses with 402 in the provider's own error shape. `request_budget` works only for a session with its own cap (otherwise it says so and points to Settings); an approved Raise budget card raises that session's cap.
- **Routes.** `POST /projects/{id}/sessions` starts a session, `GET /projects/{id}/sessions` lists a project's (newest first, `?mine=true`), `GET /sessions` lists the organization's across projects (`?mine=true`). `/experiments*`, `/evaluations*`, `/trials/*`, the value and report routes, `/spend`, `/tools`, the code-host webhook, `/runner/sessions/{id}/results` and `POST /sessions` are gone.
- **Roles are unchanged:** an organization role (viewer, editor, owner) with a per-project override. In a project any editor may message or stop any session of it; viewers read. Creating a project is an organization-owner action; project owners set the project's limits and roles.
- **Every session gets all connectors and the latest skills.** No per-session selection and no project skill switch. Removing a skill, connector or plugin part is no longer blocked by "in use".
- **`antilog mcp` and the REST tool endpoints are removed.** The CLI is `antilog runner` only; a session's agent reaches Antilog through `/mcp/sessions/{id}`.
- **The code host is removed:** the `CodeHost` trait, its webhook and the pull-request tables. A pull request comes later, from the agent with the repo's credentials.
- **Cards that stay:** raise_budget, add_credential, attach_repo, change_environment, ask_first, use_connector_tool, each with per-kind policy. Removed: seal_experiment, open_pull_request, keep_going, continue_on_another_agent, and the value-model approvals.
- **The holdout path is removed from the runner:** `Command::Run`, `RunSpec`, `RunResult`, `SessionMachine`, `QueueMachine`, the runner's `machine.rs`, `RUN_LABEL` and the sweep. Spend kinds are tokens and machine.
- **The migration clears the session area.** `20261121000000_cloud_sessions_only.sql` drops the judge tables, experiments, evaluation templates, per-experiment selections and project skill switches, keeps projects, project roles and limits, empties sessions (there are no customers) and adds the session columns above.
- **Plugins are skills and connectors;** evaluation templates are dropped.
- **Live events carry no experiment id:** `hello`, `resync`, `message`, `session` and `cards`.
- **Advisory ignore removed:** a stale `deny.toml` ignore for a `chrono` advisory is gone.

- **Tool calls in the conversation (owner, 21 Nov):** the session page copies Claude Code's cloud UI. Consecutive tool calls between two messages fold into one muted group line ("Ran 19 commands (1 failed)", with "Edited N files", "Read N files", "Called <tool> N times" and, for mixed kinds, "Ran N steps"); the latest group is open and reads "Running… N commands" while the agent works. The server therefore stores, per tool call, a label, a status and its input and output cut to 4 KB with credentials removed; this reverses "store no tool output" for those 4 KB (whole output and raw logs stay in the machine). A call is recorded when it ends, so a running group is derived (it is the last block and the session is Working) and `session_events` stays append-only. The Antilog MCP tools are recorded by the server's endpoint with their input and answer, and the runner drops OpenCode's `antilog_*` copy, so each shows once under its Antilog name.
- **Overview panel (owner, 21 Nov):** the Details panel is now the Overview: Environment (name and repos), Spend (the session's own), Connectors and Outputs (files, patches, pull requests), each linking to its page. The API does not serve the branch, context use or outputs, so the web app leaves those rows out and the board draws them as the target.

- **Changes tab (owner, 21 Nov):** the session's Changes panel copies Claude Code's cloud diff view. At the end of every agent turn, and when the session is let go, the runner reads each repo of the machine against the commit it was cloned at (the base) and sends one report: up to 50 commits since (sha, subject, time), the files of `git diff <base>` through a copy of the index with untracked files added, so new files count and ignored files never do, and the files of each commit against its parent. The server keeps the latest report per session and repo (`session_changes`, `session_commit_changes`, replaced on each report) and serves `GET /sessions/{id}/changes` and `GET /sessions/{id}/changes/commits/{sha}` to anyone who may read the session; a `changes` live event tells an open tab to refetch. This reverses "the server stores no diff" for these reports (the owner's task of 21 Nov); the code stays out of the audit log and the conversation, and the Postgres rows are the Changes panel's view of the machine, replaced by the next report.
- **Changes details, on the orchestrator's recommendation:** per-commit diffs are stored (a released machine cannot answer later) rather than fetched by a second call to the runner; one file's patch is the unified diff with three lines of context (`-U3`), so the panel shows hunks and counts the unmodified lines between them but cannot expand them until the server sends fuller context; renames are shown as a removed and an added file (`--no-renames`); a binary file shows "Binary file not shown"; the caps are 2 MB of patch text for a repo's all-changes diff and 2 MB for its commit diffs together (past it a file keeps its counts, loses its patch and shows "Too large to show"), and a diff of more than 200,000 changed lines is sent without patches; the runner and the server both enforce the caps. The header reads "base → head branch" with the repo, or "base working tree" when the agent never left the base branch; a session with several repos picks one in the header. The Playwright flow tests do not cover session panels, so none was added.

## Not in v0

Experiments and the judge (parked, `daa445f`), a pull request opened by Antilog (the agent opens it with the repo's credentials), nested sessions, throwaway cloud environments for testing, harnesses other than OpenCode, translating between model formats, harness-native plugins, Kubernetes and Helm as a requirement.

## Build rule

Delete code that a decision here makes irrelevant in the same change that replaces it. A change is not done while what it replaced is still there.
